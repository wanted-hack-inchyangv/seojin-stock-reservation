# ADR 0001: 재고 갱신에 비관적 잠금 대신 낙관적 잠금을 쓴다

## 상태

Accepted

## 배경

재고 예약(`reserve`)은 "재고 확인 -> reserved 증가"를 하나의 원자적 연산으로 처리해야
한다. 동시 요청이 같은 SKU 를 두고 경쟁할 때 두 가지 구현 방식을 검토했다.

1. **비관적 잠금 (pessimistic locking)**: RDB 라면 `SELECT ... FOR UPDATE` 로 재고 행을
   잠그고, 트랜잭션이 끝날 때까지 다른 트랜잭션은 대기한다.
2. **낙관적 잠금 (optimistic locking / OCC)**: 재고 행에 `version` 컬럼을 두고, 읽은
   버전과 쓰는 시점의 버전이 같을 때만 갱신을 반영한다(compare-and-set). 버전이
   달라졌으면 재시도한다.

## 결정

낙관적 잠금 + 제한된 횟수의 재시도를 선택했다.

## 근거

- **임계 구역이 매우 짧다.** 재고 갱신은 "읽기 -> 산술 연산 -> 쓰기" 세 단계뿐이고
  외부 I/O 를 기다리지 않는다. 이런 짧은 임계 구역에서는 잠금을 쥐고 대기하는 비용이
  재시도 비용보다 오히려 크다.
- **커넥션 풀 고갈을 피할 수 있다.** 비관적 잠금은 잠금을 쥔 커넥션이 트랜잭션이 끝날
  때까지 반환되지 않는다. 인기 SKU 에 요청이 몰리면 대기 중인 커넥션이 풀을 채워
  다른 요청까지 지연시킬 수 있다. 낙관적 잠금은 충돌한 요청만 재시도하고 커넥션을
  곧바로 반환한다.
- **읽기 경합에 강하다.** `GET /stocks/:sku` 처럼 순수 조회는 잠금과 무관하게 항상
  즉시 응답할 수 있다.
- **실패 모드가 명확하게 구분된다.** "재고가 실제로 부족해서 실패"와 "버전 충돌로
  재시도 상한을 넘겨서 실패"를 서로 다른 예외(`InsufficientStockError` vs
  `ConcurrencyConflictError`)로 나눌 수 있어, 클라이언트가 재시도해야 하는 상황과
  절대 재시도해서는 안 되는 상황을 구분해 응답할 수 있다.

## 트레이드오프

- **핫 키(hot key) 아래에서 재시도 횟수가 요청 수에 비례해 늘어난다.** 하나의 SKU 에
  극단적으로 많은 동시 쓰기가 몰리면(`test/concurrency.test.ts` 의 200건 동시 예약
  테스트가 이를 보여준다), 늦게 커밋되는 요청일수록 앞선 성공 횟수만큼 재시도를
  거쳐야 한다. 이는 OCC 의 구조적 특성이며, 비관적 잠금이었다면 대기 시간으로
  나타났을 비용이 여기서는 재시도 횟수로 나타난다.
- **쓰기 증폭.** 충돌이 잦으면 같은 갱신을 여러 번 다시 계산해야 하므로 CPU/IO 를
  더 쓴다. 우리 도메인에서는 계산 자체가 가벼워 문제가 되지 않는다고 판단했다.
- **재시도 상한(`maxRetries`)을 잘못 잡으면 정상 요청도 실패한다.** 그래서
  `ReservationService` 생성 시점에 상한을 주입할 수 있게 하여, 평소 트래픽과 세일
  이벤트처럼 특정 SKU 에 경합이 몰릴 것으로 예상되는 상황을 다르게 설정할 수 있게
  했다.

## 향후 검토할 대안

- 카운터를 여러 샤드로 쪼개고 합산해서 단일 행 경합 자체를 줄이는 방법
  (예: Redis 에서 SKU 당 여러 개의 카운터 키를 두고 해시로 분산).
- 알려진 인기 SKU 한정으로 세일 기간에만 비관적 잠금으로 전환하는 하이브리드 전략.
- 데이터베이스 네이티브 원자적 연산(예: Postgres `UPDATE ... SET reserved = reserved + 1
  WHERE reserved + $qty <= quantity RETURNING *`)으로 애플리케이션 레벨 재시도 루프
  자체를 없애는 방법. 다만 이 방식은 "재고 부족"과 "버전 충돌"을 구분하기 어려워지는
  절충이 있다.
