# ADR 0002: 예약 TTL 설계

## 상태

Accepted

## 배경

`reserve()` 로 선점한 재고는 사용자가 명시적으로 `confirm`/`release` 하지 않는 한
어딘가에서 회수되어야 한다. 그렇지 않으면 결제를 포기한 사용자의 장바구니가 다른
구매자의 재고를 영구히 잠가버린다. TTL(time-to-live) 을 어디에 두고, 만료는 누가
언제 처리할지 결정해야 했다.

## 결정

- TTL 은 **예약 생성 시점에 요청자가 지정**하고(`ttlMs`, 선택), 지정하지 않으면
  서비스 기본값(5분)을 쓴다. TTL 을 예약 단위로 둔 이유는 "장바구니 담기"와
  "결제 페이지 진입" 처럼 도메인 이벤트마다 필요한 유예 시간이 다를 수 있기
  때문이다.
- 만료 처리는 **읽는 시점의 지연 판정(lazy check) + 별도의 sweeper(백그라운드
  청소기)** 를 함께 쓴다.
  - `confirm()` 은 만료된 PENDING 예약을 만나면 즉시 `ReservationExpiredError`
    (HTTP 410) 를 던진다. 이 경로는 sweeper 가 아직 돌기 전이라도 "이미 죽은
    예약"을 확정시키는 사고를 막는다.
  - `ReservationSweeper.sweepOnce()` 는 TTL 이 지난 PENDING 예약을 찾아 `EXPIRED`
    로 전환하고 `stock.reserved` 를 회수한다. 주기적으로 (`setInterval`) 또는
    수동으로 호출할 수 있다.

## 근거

lazy check 만으로는 부족하다: 아무도 `confirm`/`release`/`GET` 을 호출하지 않는
예약은 영원히 PENDING 으로 남아 재고를 계속 붙잡는다. 반대로 sweeper 만으로는
부족하다: 스윕 주기 사이의 틈에서 이미 만료된 예약을 `confirm` 하려는 요청이 들어올
수 있다. 두 메커니즘을 함께 두어 "재고가 새는 시간(만료됐지만 아직 회수 전)"을
스윕 주기 이하로 제한하면서, 동시에 만료된 예약이 실수로 확정되는 것을 막는다.

## TTL 값 선택

기본값 5분은 "사용자가 결제 수단을 입력하는 동안 재고를 붙잡아 두는 데 필요한
현실적인 시간"을 기준으로 잡았다. 값 자체보다 중요한 것은 **호출자가 도메인 이벤트
단위로 TTL 을 다르게 줄 수 있게 열어 둔 것**이다:

| 시나리오                     | 권장 TTL 예시 |
| ----------------------------| -------------|
| 장바구니 담기                | 30분 ~ 수 시간 |
| 결제 페이지 진입(주문서 작성) | 5 ~ 15분      |
| 재시도가 잦은 배치성 주문     | 수십 초       |

## 트레이드오프

- **TTL 을 너무 짧게 잡으면** 정상적으로 결제 중인 사용자의 예약이 sweeper 에 의해
  회수되어 "결제 직전에 품절" 경험을 만들 수 있다.
- **TTL 을 너무 길게 잡으면** 결제를 포기한 사용자의 재고가 오래 묶여 실질적인
  가용 재고가 줄어든다.
- **sweeper 주기와 TTL 의 관계**: sweeper 주기가 TTL 보다 훨씬 길면 만료 후 회수까지
  지연이 커진다. 기본 스윕 주기(30초)는 기본 TTL(5분)보다 훨씬 짧게 잡아, 만료된
  재고가 최대 30초 안에는 회수되도록 했다.
- **시계 신뢰**: 만료 판정은 서버 시계(`Date.now()` 를 주입 가능하게 분리했다 - 테스트에서는
  `vi.useFakeTimers()` 로 대체한다)에 의존한다. 여러 인스턴스로 수평 확장할 경우
  인스턴스 간 시계 오차(clock skew)가 크면 판정이 흔들릴 수 있으므로, 실제 배포에서는
  NTP 동기화를 전제로 한다.

## 향후 검토할 대안

- sweeper 를 메시지 큐의 지연 메시지(delayed message)나 DB 의 TTL 인덱스로 대체해
  애플리케이션 프로세스가 직접 폴링하지 않게 하는 방법.
- 예약 생성 시 클라이언트가 지정한 TTL 의 상한/하한을 서버가 검증하는 정책
  (현재는 양의 정수라는 것만 검증한다).
